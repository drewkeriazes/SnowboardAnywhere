- Start with `docs/HANDOFF.md` (current state and next steps) and `docs/BOARD.md` (how the kanban works; the board is GitHub Projects https://github.com/users/drewkeriazes/projects/2 with one issue per card: Drew says "build FEAT-012", the session builds it on a branch, references the id in the commit, and opens a PR with `Fixes #N` so merging closes the issue; new asks get a new issue first). Research and data notes: `docs/README.md` index, `docs/data/vail-raw-data-inventory.md` before touching raw data, `docs/research/*.md` before starting a milestone. The claude.ai Project docs are a mirror; the repo copy is canonical.
- Data hosts (USGS, Planetary Computer, Overpass, Mapterhorn, usgs-lidar-public) are NOT reachable from the cloud sandbox. Fetch runs on Drew's PC; processing runs anywhere on the staged raw files.
- Canonical checkout on Drew's PC: `C:\Users\Drew\git\SnowboardAnywhere`. Raw Vail data (1.4 GB, complete 2026-11-05) is at `C:\Users\Drew\Documents\snowboard-sim\raw\vail`; `fetch.ps1 -RawDir <dir>` and `build_pack.py <slug> <raw_dir> <out_dir>` take the location as an argument, or move it to `raw\` inside the repo (gitignored). Every session attaches the same GitHub repo (drewkeriazes/SnowboardAnywhere) and commits to it; nothing lives only in a sandbox.
- Pipeline flow: `pipeline/resorts/<slug>.json` -> `gen_manifest.py` -> `manifests/<slug>.json` -> `fetch.ps1` -> `raw/<slug>/` -> `build_pack.py` -> `packs/<slug>/` -> the game loads `/packs/<slug>/` (Vite dev middleware serves `../packs`). `synth_pack.py` writes a synthetic mountain in the same format for client work without real data.
- Do not run two fetches at once; the downloader assumes a single writer.
- All game-space coordinates are local metres: pack x east, y north, z up; three.js x east, y up, z = -north. Never put lat/lon in the renderer or physics.
- Docs travel with the change: a PR that changes what a player or developer sees updates the docs in the same PR. Keys, modes, cameras or setup steps go in `README.md` (controls table, modes, Play). Features, code layout, test tools, pipeline scripts or URL parameters go in `docs/developer-guide.md`. A PR with nothing user-facing (refactors, internal fixes, tuning) leaves them alone.
- Checks: CI runs the full set on every PR (`.github/workflows/checks.yml`: typecheck, build, pytest, the physics and synth-pack browser checks, stills with shader compile and scene budgets against `main`, repo rules, public repo guards; `docs/developer-guide.md` > Checks in CI), and the reviewer reads the results. Before pushing, run only the fast typecheck for what you touched (`cd game && npx tsc --noEmit`, or `cd pipeline && python -m pytest tests`). Run locally only what CI can't (real-pack stills and checks, `perf-check`, anything that needs the GPU), always on the GPU on Drew's PC, never `--cpu`, and say in the PR what you ran. Render check: `cd game && npx vite build && node tools/shoot.mjs <pack>` (headless; real GPU by default on Drew's PC, SwiftShader plus automatic `lowgfx` in the cloud; the first line prints which), or add `--headed` on Drew's PC to watch it.
- Do not assert Bonvo internals from memory; the verified capture is in the plan doc.
- No em dashes in prose.
- Commit messages: plain, no `Co-Authored-By` or session-link trailers. Commits are authored as Drew.
- Parallel sessions: one git worktree and branch per card (`issue-<number>-<slug>`), land through a PR, never commit in another session's checkout or push to `main` directly. Details in `docs/BOARD.md` > Parallel sessions.
