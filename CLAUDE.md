# SnowboardAnywhere – working notes for Claude

- Stack: Three.js 0.172 + TypeScript + Vite in `game/`. **This repo plays resort packs; it does not build them** (EPIC-16): the pipeline (Python, the fetch scripts, resort configs, the `.cmd` launchers, the pack-build skill) lives in the sibling clone `C:\Users\Drew\git\MapPacker-SnowboardAnywhere` (https://github.com/drewkeriazes/MapPacker-SnowboardAnywhere), which publishes packs as releases. Pipeline work is a MapPacker card and PR, under that repo's `CLAUDE.md`. Python here is only `tools/` and `tools/ci/` helpers and `game/tools/prep_textures.py` (the game's own rock textures).
- Start with `docs/HANDOFF.md` (current state and next steps) and `docs/BOARD.md` (how the kanban works; the board is GitHub Projects https://github.com/users/drewkeriazes/projects/2 with one issue per card, pulling issues from this repo and drewkeriazes/MapPacker-SnowboardAnywhere (the pipeline, resort data and packs, EPIC-16): Drew says "build FEAT-012", the session builds it on a branch, references the id in the commit, and opens a PR with `Fixes #N` so merging closes the issue; new asks get a new issue first; a problem found along the way gets filed without asking, after searching the board for an existing card: `docs/BOARD.md` rule 3). Plan of record: `docs/bonvo-teardown-and-build-plan.md` (verified Bonvo capture, data sources, milestones). Pack layout: MapPacker's [`docs/pack-format.md`](https://github.com/drewkeriazes/MapPacker-SnowboardAnywhere/blob/main/docs/pack-format.md) (FEAT-239: the spec, and the Contract of values both repos hold). Research and data notes: `docs/README.md` index, `docs/research/*.md` before starting a milestone (`docs/data/` and the pipeline research describe the pipeline as it was when it lived here). The claude.ai Project docs are a mirror; the repo copy is canonical.
- Canonical checkout on Drew's PC: `C:\Users\Drew\git\SnowboardAnywhere`. Every session attaches the same GitHub repo (drewkeriazes/SnowboardAnywhere) and commits to it; nothing lives only in a sandbox. The raw data MapPacker builds from still sits in this checkout's `raw/` (gitignored; MapPacker's `SBA_RAW_ROOT` points here until it moves): leave it alone.
- Packs: `cd game && npm run get <slug>` downloads a published pack into `packs/<slug>/` (`npm run get synth` is the synthetic test mountain CI runs on); `npm run get -- --from <MapPacker>/packs/<slug>` copies in a pack built in MapPacker so it can be ridden before it is published. Never junction or symlink a folder into a worktree's `packs/`: `git worktree remove` follows it and empties the target. Remove a worktree with `node tools/rm_worktree.mjs ../wt<n>` from the main checkout, never a bare `git worktree remove` (BUG-093: it unlinks the worktree's junctions, such as a junctioned `game/node_modules`, first; `docs/BOARD.md` > Parallel sessions). The game loads `/packs/<slug>/` (Vite dev middleware serves `../packs`). The pack format is the contract between the repos: `PACK_FORMAT` in `game/src/pack/format.ts` and MapPacker's `FORMAT_VERSION`; a change a current pack can't satisfy needs both PRs, the game's first or together.
- All game-space coordinates are local metres: pack x east, y north, z up; three.js x east, y up, z = -north. Never put lat/lon in the renderer or physics.
- Docs travel with the change: a PR that changes what a player or developer sees updates the docs in the same PR. Keys, modes, cameras or setup steps go in `README.md` (controls table, modes, Play). Features, code layout, test tools or URL parameters go in `docs/developer-guide.md`. A PR with nothing user-facing (refactors, internal fixes, tuning) leaves them alone.
- Checks: CI runs the full set on every PR (`.github/workflows/checks.yml`: typecheck, build, the physics and synth-pack browser checks, shader compile and scene budget counts against `main`, before / after stills on request, repo rules, public repo guards; `docs/developer-guide.md` > Checks in CI), and the reviewer reads the results. Before pushing, run only the fast typecheck (`cd game && npx tsc --noEmit`). Run locally only what CI can't (real-pack stills and checks, `perf-check`, anything that needs the GPU), always on the GPU on Drew's PC, never `--cpu`, and say in the PR what you ran. On Drew's PC a plain `git push` to an open PR that changes `game/` runs CI's `render-budgets` on the GPU first through the pre-push hook (`.githooks/pre-push`, FEAT-183; it never blocks the push), and CI skips its own run for that commit; `node tools/ci/local_render_budgets.mjs --push` does the same by hand (FEAT-176, `docs/developer-guide.md` > Checks in CI). Cloud sessions just push. Render check: `cd game && npx vite build && node tools/shoot.mjs <pack>` (headless; real GPU by default on Drew's PC, SwiftShader plus automatic `lowgfx` in the cloud; the first line prints which), or add `--headed` on Drew's PC to watch it.
- Do not assert Bonvo internals from memory; the verified capture is in the plan doc.
- No em dashes in prose.
- Commit messages: plain, no `Co-Authored-By` or session-link trailers. Commits are authored as Drew.
- Parallel sessions: one git worktree and branch per card (`issue-<number>-<slug>`), land through a PR, never commit in another session's checkout or push to `main` directly. Details in `docs/BOARD.md` > Parallel sessions.
- Dev servers on demand (FEAT-174): start a Vite dev server only when a check needs one or the change is ready for Drew to test, never at the start of a session. One per worktree, on a free port with `--strictPort`; give Drew the URL. Stop it when Drew is done testing or the PR merges, and before removing the worktree. Headless checks (`shoot.mjs`, the `*check.mjs` tools) start and stop their own server, so they need none. The `threejs-devtools` MCP is off by default (`.claude/settings.json`); turn it on in `/mcp` only for a scene-inspection session.
- Docs-first PRs (BUG-089): when a PR's first push is docs only, open it as a draft and mark it ready once the code is in, so the reviewer sees the whole diff. Cloud sessions mark it ready through REST, not `gh pr ready`; see `docs/BOARD.md` rule 2.
- PR review comments: the Claude reviewer bot comments on every PR. When Drew replies "yes" on one (or posts "yes" / "yes 1" as a PR comment for items in the summary), `.github/workflows/pr-feedback.yml` applies and pushes it on its own. For thumbs-ups, use the `pr-feedback` skill: apply the liked ones in one commit and one push, then reply on each comment.
- Spotify private branch (FEAT-142, #308): in-game Spotify breaks Spotify's Developer Policy, so it never goes on `main` and the branch `spotify-private` is **local only on Drew's PC: never push it** (the repo is public). Keep it current: whenever a PR merges to `main`, a session on Drew's PC runs this in the branch's worktree (create it once with `git worktree add ..\SnowboardAnywhere-spotify spotify-private`): `git fetch origin && git merge origin/main`, fix conflicts, then `cd game && npx tsc --noEmit`. Merge, don't rebase. This is a manual step: the local `post-merge` hook that used to do it stops running once `core.hooksPath` points at `.githooks` (FEAT-183), so Drew triggers the merge himself when he wants the branch current. Cloud sessions can't see the branch and skip this.
